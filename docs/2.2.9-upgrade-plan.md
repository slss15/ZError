# ZError 2.2.9 升级方案

- 版本：2.2.9
- 日期：2026-10-29
- 状态：待确认
- 目标平台：Windows 10/11 x64
- 关联版本：2.2.8 云端未签名 NSIS 包

## 1. 背景与现象

2.2.8 安装后出现以下问题：

1. AI 模型响应里已经能看到结果，但请求状态仍显示“处理中”。
2. 请求记录中的响应时间异常：既有 12ms，也有 19s、49s、174s、176s。
3. 有时答案似乎先于联网搜索出现。
4. 无法判断最终发给模型的 prompt 是否真的包含搜索结果。

已确认的运行时数据：

- 题库精确命中时响应时间约 12ms，属于正常。
- 带搜索的普通请求约 19s，其中 Exa 搜索约 12–13s，模型约 3–6s。
- 16:07:21 和 16:07:23 两条请求分别在 174s、176s 后结束，且几乎同时完成。
- 直连当前模型测试同类问题，模型 3–6s 即可结束；搜索 5–13s 即可返回。
- 因此 174s 不是模型本身耗时，更像是请求在后台排队/被挂起后一起执行。

## 2. 根因分析

### Critical 1：同题判重被当成最终响应收口

`Home.vue` 中 `handleSameQuestionCheckRequest()` 复用 `sendModelResponseToBackend()`。该函数会：

- 写入 `finalModelResponseState`
- 调用 `applyLocalRequestCompletion()`
- 提前设置请求 `status`、`stage=completed`、`responseTime`

但同题判重只是内部中间步骤，不是最终答案。结果是：

- 判重 JSON 先出现在“AI 模型响应”中；
- 请求可能提前显示 200 或短耗时；
- 真正的搜索、最终答题还在后面；
- 后续最终响应与前端本地状态、后端 completed 事件互相覆盖，造成“结果已出但仍在处理中”或响应时间跳变。

### Critical 2：搜索注入不可验证，失败被静默降级

`runSearchForRequest()` 捕获异常后返回 `null`，`callModelAPI()` 继续用普通 prompt 调模型。当前没有：

- 记录搜索是否成功；
- 记录搜索结果是否真正进入 prompt；
- 在 UI 标记“本次未使用搜索”；
- 阻止搜索未完成时发送最终答案。

最终答题路径本身是 `await` 搜索后才调用模型的，所以正常情况下不会“没搜完就出答案”。用户看到的提前答案，主要来自判重阶段输出，或搜索失败后的降级作答。

### Major 1：模型调用运行在前端 WebView

模型调用、流式解析、最终响应上报都发生在 Vue WebView 中。窗口最小化、被遮挡或处于后台时，Windows 可能对 WebView2 做后台计时器节流、渲染挂起或遮挡计算，导致：

- SSE/Tauri 事件延迟处理；
- 模型调用排队；
- 最终响应延迟上报；
- 后端把等待时间全部算进 `response_time`；
- 两条请求在窗口恢复后同时完成。

`app_activity.rs` 目前只为 macOS 做了防 App Nap，Windows 没有对应处理。

### Major 2：40 秒总超时 + 2 次重试放大耗时

`callModelWithStreaming()` 使用固定总超时：40 秒。流只要超过 40 秒就被 abort，然后按配置重试 2 次，最多 3 次：

- 3 × 40s = 120s；
- 再叠加同题判重（最多 45s）和搜索（最多 30s），可接近或超过后端 180s 绝对上限；
- 活跃但较长的流会被误杀，产生“结果已出现但状态仍处理中”。

### Major 3：SSE 结束标记未主动终止

`modelProtocol.ts` 的 `readSSEPayloads()` 遇到 `[DONE]` 只是 `continue`，没有结束读取；同时没有在 `finish_reason`、`message_stop`、`response.completed` 时主动停止。若服务端发送结束标记后不主动关闭连接，就会一直等到超时。

### Minor 1：响应时间没有阶段归因

后端 `response_time` 是 `/query` 的总墙钟时间，包含：

- 题库匹配；
- 同题判重；
- 搜索；
- 模型生成；
- 前端后台等待/排队；
- 最终上报。

UI 只显示一个总时间，容易被误认为模型生成时间。

### Minor 2：RequestLogs 持久化是死代码

`database.rs` 中存在 `insert_request_log()`，但 `logger.rs` 没有调用它，导致 `RequestLogs` 表始终为空；UI 依赖内存/SSE 日志。2.2.9 不一定要恢复该表，但诊断日志必须独立持久化。

## 3. 目标与非目标

### 目标

1. 请求状态只在最终响应落定后收口；判重阶段不再提前完成/计时。
2. 搜索成功、失败、超时、是否注入 prompt 全部可验证、可展示。
3. 最终答案发送前必须确认搜索阶段已结束；搜索未完成不得出最终答案。
4. Windows 后台最小化时模型调用不被 WebView 节流/挂起。
5. 长流不再因 40 秒总超时被误杀重试；重试次数可解释。
6. 响应时间可拆分为题库、判重、搜索、模型、后台等待。
7. 提供可持久化、可轮转、脱敏的诊断日志。
8. 2.2.9 通过云端工作流发布未签名 NSIS 包。

### 非目标

- 2.2.9 不把模型调用整体迁移到 Rust。该改造工作量大，留到 3.0。
- 不恢复 2.2.8 的 updater 签名；仍按现有流程发布未签名包。
- 不改 OCS 对接协议和 `/query` 响应结构。

## 4. 方案总览

```text
received
  -> db_exact ──命中──> completed(200, ms)
  -> db_candidates
  -> same_check (内部，不落最终状态)
  -> search (成功/失败/超时，必须 settled)
  -> answering (文本/总结/视觉)
  -> reporting (只允许最终响应)
  -> completed(200/408/500)
```

核心原则：

- 只有 `reporting` 阶段可以写 `status`、`stage=completed`、`responseTime`。
- 判重、搜索、模型中间试错都只写诊断日志，不写请求最终状态。
- 最终答案发送前检查 `searchSettled` 和 `searchInjected`。

## 5. 详细设计

### 5.1 请求状态机与判重隔离

前端 `RequestLog` 增加：

```ts
type RequestPhase =
  | 'received'
  | 'matching'
  | 'same_check'
  | 'searching'
  | 'answering'
  | 'reporting'
  | 'completed'
  | 'error'
  | 'timeout'

interface RequestLog {
  phase?: RequestPhase
  sameCheck?: {
    startedAt: number
    durationMs?: number
    result?: string
    error?: string
  }
  timings?: {
    dbMs?: number
    sameCheckMs?: number
    searchMs?: number
    modelFirstTokenMs?: number
    modelTotalMs?: number
    reportMs?: number
    hiddenMs?: number
  }
}
```

改造 `sendModelResponseToBackend()`：

```ts
type ResponsePhase = 'intermediate' | 'final'

sendModelResponseToBackend(requestId, content, isSuccess, reasoning, {
  phase: 'intermediate' | 'final'
})
```

- `phase='intermediate'`（判重）：
  - 只 POST `/api/model/response`，让后端 `wait_for_model_response` 解锁；
  - 不写 `finalModelResponseState`；
  - 不调用 `applyLocalRequestCompletion()`；
  - 不设置 `status`、`responseTime`；
  - 判重结果写入 `log.sameCheck`，在 UI 标为“题目判重（内部）”。
- `phase='final'`：
  - 沿用最终状态收口；
  - 发送前执行搜索门禁（见 5.2）。

`callModelAPI()` 开始时：

- 如果 `log.phase` 是 `same_check` 或中间态，重置为 `answering`；
- 不清空后端权威状态，但清空前端由判重误写的 `status/responseTime`；
- 最终 `request-log-complete` 到达时以事件为准。

### 5.2 搜索注入校验与最终答案门禁

`searchService.ts` 的 `SearchTrace` 增加：

```ts
interface SearchTrace {
  status: 'searching' | 'success' | 'error'
  injected: boolean
  injectedTo: Array<'text' | 'summary' | 'vision'>
  contextChars: number
  query: string
  error?: string
  durationMs?: number
}
```

注入点：

- 文本模型：`callModelWithStreaming()` 合并 `searchContext` 后，检查最后一条 user message 是否包含 `【联网搜索结果】`；设置 `injected=true`、`injectedTo.push('text')`。
- 总结模型：`summaryQuery` 拼接后检查；设置 `injectedTo.push('summary')`。
- 视觉模型：`multimodalContentWithSearch` 中加入文本块后检查；设置 `injectedTo.push('vision')`。

最终门禁：

```ts
await searchSettledPromise
if (searchConfig.enabled && !searchTrace) {
  // 应当已降级，记录 warning
}
if (searchTrace?.status === 'searching') {
  // 不允许发送最终答案，等待或超时
  throw new Error('搜索尚未完成，暂不发送最终答案')
}
if (searchTrace?.status === 'success' && !searchTrace.injected) {
  // 代码缺陷：记录 error，重试注入一次；仍失败则标记 search_used=false
}
```

设置项 `search.failOpen`：

- 默认 `true`：搜索失败继续作答，但 UI 必须显示“搜索失败，未注入”。
- `false`：搜索失败直接把本题置为 500，并返回明确错误，不发送无搜索答案。

设置项 `search.required`（可选）：

- 开启后搜索结果必须 ≥ 1 条才允许最终作答；否则按失败处理。

### 5.3 Windows 后台节流处理

主窗口创建时优先使用 Tauri 2 的 `background_throttling` 能力：

```rust
// lib.rs，Windows 主窗口
.background_throttling(BackgroundThrottlingPolicy::Disabled)
```

如果当前 Tauri 版本不支持或行为不稳定，增加 WebView2 参数：

```text
--disable-background-timer-throttling
--disable-renderer-backgrounding
--disable-backgrounding-occluded-windows
--disable-features=CalculateNativeWinOcclusion
```

实现时先确认 Tauri 2.9.3 的 `WebviewWindowBuilder` API，再选择最小改动方案；两种方式都需在 2.2.9 实机验证。

同时增加：

- `document.visibilitychange` → 写 `visibility_hidden`/`visibility_visible` 诊断日志；
- 进入 hidden 时记录时间，恢复时计算 `hiddenMs`；
- 请求完成时如果 `hiddenMs > 3s`，详情页显示“其中后台等待 X 秒”。

### 5.4 超时、重试与 SSE 结束

前端 `callModelWithStreaming()`：

- 固定 `setTimeout(timeoutMs)` 改为 **inactivity timer**：
  - 每收到 content/reasoning 重置；
  - 无新 token 超过 `modelResponseTimeout` 才 abort；
  - 单独设置绝对上限 `modelAbsoluteTimeout`（默认 300s）。
- 重试策略：
  - 首次 token 前失败/超时：可按 `modelRetryCount` 重试；
  - 已收到内容但未收到完整答案：最多重试 1 次；
  - 已收到包含 `{"answer": ...}` 的完整答案：不再重试，直接作为成功结果；
  - 每次重试写诊断日志（attempt、原因、已收到内容长度）。

后端 `model_wait_budget_secs()`：

- inactivity 仍按 `modelResponseTimeout + 20s`；
- absolute 改为包含同题判重和搜索预算：

```text
absolute = modelAbsoluteTimeout
         + searchTimeoutSeconds
         + sameCheckBudget(45s)
         + 60s buffer
```

避免 174s 撞 180s 上限。

`modelProtocol.ts` 的 `readSSEPayloads()`：

- 遇到 `[DONE]` 立即结束；
- 遇到 OpenAI Chat `finish_reason` 非空时，yield 后结束；
- 遇到 Anthropic `message_stop` 结束；
- 遇到 Responses `response.completed` / `response.failed` 结束；
- 增加 mock 测试：发送内容后保持连接不关闭，客户端仍能及时结束。

### 5.5 诊断日志

新增 `src-tauri/src/diagnostics.rs` + `src/services/diagnosticLogger.ts`。

日志路径：

```text
%LOCALAPPDATA%\ZError\logs\app-YYYYMMDD.jsonl
```

规则：

- JSONL，一行一个事件；
- 按天轮转，单文件上限 10MB，保留 7 天；
- 不记录 API Key、Authorization、完整 prompt；
- 默认记录问题/选项摘要、搜索结果数、耗时、错误、阶段；
- 可选“详细日志”开关，开启后记录 prompt 长度和哈希，不记录正文。

事件类型：

```text
request_received
db_exact
db_candidates
same_check_start
same_check_end
search_start
search_end
search_injected
model_dispatch
model_first_token
model_retry
model_end
final_post
backend_complete
visibility_hidden
visibility_visible
```

示例：

```json
{"ts":"2026-10-29T16:14:21.556+08:00","level":"info","scope":"search","request_id":"84c7d8f4","event":"search_start","data":{"mode":"remote","tool":"web_search_exa","query_len":42,"visibility":"visible"}}
{"ts":"2026-10-29T16:14:33.752+08:00","level":"info","scope":"search","request_id":"84c7d8f4","event":"search_end","data":{"status":"success","results":5,"duration_ms":12196,"injected":true,"context_chars":3708}}
```

Tauri 命令：

- `append_diagnostic_log(level, scope, event, requestId, data)`
- `open_log_dir()`
- `get_log_path()`

请求详情新增“诊断”页：

- 时间线；
- 分段耗时；
- 搜索是否注入；
- 后台等待时长；
- 模型重试次数；
- “打开日志目录”按钮。

### 5.6 响应时间归因

请求列表仍显示后端总耗时，但增加 tooltip：

```text
总耗时 = 题库匹配 + 判重 + 搜索 + 模型生成 + 后台等待 + 上报
```

详情“诊断”页显示：

```text
题库 12ms / 判重 0ms / 搜索 12.2s / 模型 6.1s / 后台等待 0s / 总 18.7s
```

若 `total - (db + sameCheck + search + model + report) > 2s`，标记“存在后台排队/等待”。

## 7. 测试计划

### 单元测试

- `searchService`：搜索成功/失败/超时；`formatSearchContextForModel` 内容；注入标记。
- `modelProtocol`：`[DONE]`、`finish_reason`、`message_stop`、`response.completed` 结束；连接不关闭场景。
- `Home.vue` 纯逻辑：判重中间响应不调用 `applyLocalRequestCompletion`；最终响应门禁。
- Rust：`diagnostics` 轮转/脱敏；`mcp_stdio_search` 已有测试；`model_wait_budget_secs` 计算。

### 集成测试

- mock OpenAI SSE 服务：返回内容后保持连接不关闭，验证客户端及时结束且不重试。
- mock MCP：搜索慢/失败/空结果，验证 UI 标记和 `failOpen` 行为。
- mock 后端：判重响应不提前置 200，最终响应才置 200。
- 窗口最小化：发送请求后最小化，恢复后检查耗时拆分、状态更新、日志中的 hiddenMs。

### 手工验收

1. 题库精确命中：状态 200，耗时毫秒级。
2. 正常 AI + 搜索：详情显示“搜索已注入 N 条 / X 字”，总耗时 ≈ 搜索 + 模型。
3. 搜索失败：详情显示“搜索失败，未注入”，按 `failOpen` 配置继续或报错。
4. 窗口后台：最小化发送，恢复后状态立即更新，不再出现 174s 排队。
5. 判重：详情显示“题目判重（内部）”，请求状态不提前完成。
6. 日志：`app-*.jsonl` 包含完整阶段；无 API Key；详情“诊断”页时间线正确。
7. 构建：`vue-tsc --noEmit`、`npm run build`、`cargo check`、`cargo test` 全过。

## 9. 风险与后续

| 风险 | 影响 | 应对 |
|---|---|---|
| WebView2 后台节流参数在部分系统无效 | 仍可能出现后台排队 | 诊断日志 + `backgroundThrottling` + WebView2 参数双保险 |
| inactivity timeout 让极慢模型占用更久 | 单题最长等待变长 | 增加绝对上限、重试日志、可配置 |
| 判重隔离改动影响同题判断 | 同题复用异常 | 保留中间响应对后端解锁；加回归测试 |
| 搜索注入校验误判 | 阻止最终答案 | 注入失败只标记 + failOpen，不默认阻断 |
| 诊断日志含隐私 | 题目内容泄露 | 默认不记录完整 prompt；脱敏；本地保留 7 天 |

3.0 建议：把模型调用、搜索、判重下沉到 Rust 后端（tokio + reqwest），前端只负责配置和展示，彻底摆脱 WebView 后台限制。
